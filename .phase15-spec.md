# Phase 15: RBAC Multi-User Dashboard Auth

## Overview
Replace the single hardcoded DASHBOARD_USER/DASHBOARD_PASS env var login with a proper 3-tier RBAC system: OWNER → ADMIN → MEMBER.

## Database Changes

### New table: `dashboard_users`
```sql
CREATE TABLE IF NOT EXISTS dashboard_users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT UNIQUE NOT NULL,
    password_hash TEXT NOT NULL,
    display_name TEXT NOT NULL,
    role TEXT NOT NULL CHECK(role IN ('owner', 'admin', 'member')),
    staff_id INTEGER REFERENCES staff(id),
    team_scope TEXT,  -- NULL for owner (sees all), team name for admin/member
    is_active BOOLEAN DEFAULT TRUE,
    created_by INTEGER REFERENCES dashboard_users(id),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    last_login TIMESTAMP
);
```

## Backend Changes (web_dashboard_api.py)

### Auth System Overhaul
1. Replace env-var DASHBOARD_USER/DASHBOARD_PASS check with DB-backed bcrypt auth
2. JWT payload must include: `sub` (username), `role`, `team_scope`, `staff_id`, `user_id`
3. Add `get_current_user()` dependency that returns full user dict from token
4. Keep JWT_SECRET from env (already working)

### Migration/First-Time Setup
- On startup, check if `dashboard_users` table exists. If not, create it.
- If table is empty AND DASHBOARD_USER/DASHBOARD_PASS env vars are set, auto-create the first OWNER account from those env vars (bcrypt the password). This is the zero-downtime migration path.
- If table is empty and no env vars, the `/api/auth/setup` endpoint allows creating the first owner.
- After migration, env var login is IGNORED (DB takes precedence).

### New API Endpoints

#### Setup (unauthenticated, only works when 0 users exist)
- `POST /api/auth/setup` — Create first owner: `{username, password, display_name}`

#### Auth (updated)
- `POST /api/auth/login` — Now checks dashboard_users table with bcrypt
- `GET /api/auth/verify` — Returns `{ok, username, role, team_scope, display_name, staff_id}`
- `POST /api/auth/change-password` — Authenticated user changes own password

#### User Management (new)
- `GET /api/users` — List users (owner sees all, admin sees their team only)
- `POST /api/users` — Create user (owner creates any role, admin creates member in own team only)
- `PUT /api/users/{user_id}` — Update user (same RBAC constraints)
- `DELETE /api/users/{user_id}` — Deactivate user (soft delete, set is_active=false)
- `POST /api/users/{user_id}/reset-password` — Reset password (owner for anyone, admin for their members)

#### Data Scoping (modify existing endpoints)
All existing data endpoints must be scoped:
- OWNER: no filter (sees everything)
- ADMIN: filter by `team_scope` (staff.team = user.team_scope)
- MEMBER: filter by `staff_id` (only their own clients/data)

Affected endpoints:
- `/api/dashboard` — aggregate stats scoped
- `/api/funnel` — scoped
- `/api/activity` — scoped
- `/api/staff` — scoped
- `/api/clients` — scoped
- `/api/clients/{id}` — only if client belongs to user's scope
- `/api/trends` — scoped
- `/api/team/{team}/performance` — only accessible if user has that team scope
- `/api/export/*` — scoped

### RBAC Enforcement Rules
```
OWNER:
  - Can create/edit/deactivate any user (owner/admin/member)
  - Sees all data across all teams
  - Can assign any team_scope

ADMIN:
  - Can create/edit MEMBER users in their own team_scope only
  - Cannot create other admins or owners
  - Cannot edit users outside their team
  - Sees data only for their team_scope

MEMBER:
  - Cannot access /api/users endpoints at all
  - Sees only their own data (filtered by staff_id)
  - Can only change their own password
```
